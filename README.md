# BestPrice

O [contexto do produto](docs/product-context.md) define a visão de monitoramento automático de preços, tendo o Mercado Livre Brasil como marketplace exclusivo desta fase (a premissa anterior era a Amazon). Esta branch implementa um fluxo inicial para publicações MLB: entrada por URL, histórico, dashboard, alertas e notificações em FastAPI, React e PostgreSQL. A integração real com anúncios de terceiros permanece desabilitada por padrão até validar autorização externa e configurar um token OAuth operacional.

## Preparar e executar localmente

Pré-requisitos: Python 3.13, uv, Node.js 22, npm e Docker Compose.

1. Copie `.env.example` para `.env` e substitua `POSTGRES_PASSWORD`.
2. Suba o banco com `docker compose up -d db`.
3. Em `backend/`, rode `uv sync --locked --extra dev`. Configure `DATABASE_URL` para o banco local, por exemplo `postgresql://bestprice:SENHA@localhost:5433/bestprice`, e execute `uv run alembic upgrade head`.
4. Ainda em `backend/`, crie uma conta com `uv run python -m app.auth.provision EMAIL`; a senha é solicitada sem eco. Inicie a API com `uv run uvicorn app.main:app --reload --port 8000`.
5. Em `frontend/`, rode `npm ci` e `npm run dev`. Abra <http://localhost:5173/login>. O Vite encaminha `/api` para a API local.

Após entrar, a interface usa `/` (Início), `/produtos`, `/produtos/:id` (detalhe de um monitoramento próprio) e `/alertas`. As telas podem ser abertas por URL, atualizadas e percorridas com voltar/avançar; visitantes retornam à rota protegida solicitada depois do login. No Compose, Nginx entrega `index.html` aos caminhos da SPA e mantém `/api/*` no proxy da API. A verificação das rotas da spec 0021 foi feita localmente; a mesma abertura direta em `stage` ainda depende de promoção e validação naquele ambiente.

Também é possível subir a stack com `docker compose up --build`. Nesse modo, o backend aplica Alembic antes de iniciar; o worker espera o backend ficar saudável. Em worktree Windows, use `./scripts/compose-worktree.ps1 up --build` para isolar portas e volume. `docker compose down` preserva os dados.

O worker usa por padrão uma consulta por publicação a cada 3600 segundos, lote de 20, uma tentativa por vez e pausa de 60 segundos entre ciclos. `.env.example` permite ajustar `MONITOR_CHECK_INTERVAL_SECONDS`, `MONITOR_FRESHNESS_SECONDS`, `MONITOR_BATCH_LIMIT`, `MONITOR_MAX_CONCURRENCY` e `MONITOR_POLL_INTERVAL_SECONDS`. Defina a frequência e a concorrência conforme os limites oficiais da integração depois de validá-la; a [arquitetura](docs/architecture.md#estado-desta-branch) mostra padrões e faixas aceitas.

`GET /api/health` responde 200 quando o banco aceita `SELECT 1`; não testa o esquema nem a API externa. Sem validação oficial para anúncios de terceiros, mantenha `MERCADOLIVRE_THIRD_PARTY_VALIDATED=false`: consultas novas à publicação retornam 503. A API ainda rejeita URL inválida, link curto, busca ou categoria com 400 e mensagem específica, informa vínculo duplicado com 409, retoma um vínculo interrompido com 200 e aplica o intervalo mínimo de atualização com 429 antes de solicitar a integração. A interface permite entrar com conta provisionada e navegar pelos dados já existentes.

O código dispõe de armazenamento cifrado e renovação OAuth da conta operadora. Para uma operação autorizada, configure `MERCADOLIVRE_CLIENT_ID`, `MERCADOLIVRE_CLIENT_SECRET`, `MERCADOLIVRE_REDIRECT_URI` e uma chave Fernet única em `MERCADOLIVRE_OAUTH_KEY`, fora do repositório. O callback HTTPS registrado no DevCenter é `https://bestprice-stage-api.onrender.com/api/marketplace/oauth/callback`; use a mesma chave Fernet com segurança no ambiente que inicia o fluxo e no Stage. O app e suas configurações de callback e permissões foram conferidos no DevCenter. O callback atualizado foi promovido para Stage pela PR #139; o serviço está Live com health 200. Três tentativas de autorização falharam, sem credencial persistida; a terceira foi classificada como `invalid_state` antes da troca de token. Client ID, redirect URI e chave Fernet foram conferidos, mas a causa da rejeição do state ainda está em investigação. Para iniciar o fluxo, execute `docker compose run --rm backend python -m app.marketplace.authorize_operator` para gerar uma URL oficial com `state` assinado; conclua a autorização na conta operadora, que retorna ao callback Stage e guarda os tokens cifrados no banco Stage. O `uv run python -m app.marketplace.provision` continua disponível para reprovisionar tokens fornecidos manualmente se uma renovação ficar bloqueada após resposta ambígua. Mantenha `MERCADOLIVRE_THIRD_PARTY_VALIDATED=false` até validar a autorização e o acesso permitido.

Para validação operacional, configure três IDs MLB distintos em `MERCADOLIVRE_VALIDATION_PRICE_ITEM_ID`, `MERCADOLIVRE_VALIDATION_NO_PRICE_ITEM_ID` e `MERCADOLIVRE_VALIDATION_UNAVAILABLE_ITEM_ID`, usando apenas anúncios de terceiros autorizados para a conta. Mantenha `MERCADOLIVRE_THIRD_PARTY_VALIDATED=false`. Com banco local saudável e migrado e tokens da conta operadora provisionados, execute `docker compose run --rm backend python -m app.marketplace.validate_live --confirm-live-requests`; a ferramenta faz três consultas somente de leitura (até seis GETs de item/preço e, quando necessário, uma renovação OAuth) e imprime JSON sem títulos, URLs nem tokens. O relatório usa `passed` somente quando os três cenários correspondem e a renovação OAuth foi observada; usa `requires_manual_action` quando faltam IDs válidos ou credenciais OAuth, um anúncio não corresponde ao cenário ou a renovação ainda precisa ser agendada. Falhas reais de consulta permanecem `failed`, mesmo se outro cenário exigir ação manual. Para confirmar renovação, execute quando a credencial provisionada estiver a até cinco minutos do vencimento. Não provoque 429: use os testes simulados para falha e recuperação e siga a cadência informada oficialmente. A sonda não demonstra cadastro/worker ponta a ponta nem ativa o flag. Registre a saída sanitizada e os limites em [verificação 0026](specs/0026-validacao-operacional-mercado-livre/verification.md). Até obter evidência real e operacional, mantenha a integração desligada.

## Verificar

Em `backend/`: `uv run ruff check .` e `uv run pytest -q`; `TEST_DATABASE_URL` habilita testes contra PostgreSQL isolado. Em `frontend/`: `npm run lint`, `npm test -- --run` e `npm run build`; a regressão visual local (Playwright, snapshots de landing, login e 404 em 320/768/1280 px, com esquema claro/escuro emulado) roda com `npm run test:visual` e não faz parte do CI. Resultados e limites estão nas verificações das specs [0013](specs/0013-monitoramento-mercado-livre-brasil/verification.md) (API e integração), [0012](specs/0012-area-usuario-monitoramento/verification.md) (área do usuário), [0021](specs/0021-navegacao-por-rotas/verification.md) (navegação por URL) e [0025](specs/0025-harness-design-tooling/verification.md) (design tooling e regressão visual).

A [documentação de onboarding](docs/index.md) detalha arquitetura, esquema, módulos e infraestrutura. O processo de contribuição usa spec, plano, implementação, verificação, PR para `develop` e revisão independente. A spec 0019 define releases no GHCR por tag SemVer no SHA validado em `stage`; o fluxo só fica ativo após integrar a mudança e aplicar as configurações externas descritas em [docs/github-workflow.md](docs/github-workflow.md). A publicação não configura implantação em produção.
