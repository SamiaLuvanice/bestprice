# Plano — 0007

## Contrato da API

| Método e rota | Entrada | Resposta | Status |
|---|---|---|---|
| `GET /api/health` | Nenhum corpo ou autenticação | `{"status":"ok","database":"ok"}` | 200 se `SELECT 1` responder no PostgreSQL |
| `GET /api/health` | Nenhum corpo ou autenticação | `{"status":"unavailable","database":"unavailable"}` | 503 se a conexão ou a consulta falhar |

JSON com `Content-Type: application/json`; os campos são obrigatórios e têm somente os valores acima. O endpoint não expõe host, usuário, senha, SQL ou stack trace. Uma falha de banco conhecida é registrada no log do servidor com contexto interno e traduzida para 503. A indisponibilidade da própria API aparece na interface como falha de conexão, sem inventar uma resposta HTTP. A interface deve tratar tanto 503 quanto falha de rede e mostrar uma mensagem compreensível; só mostra sucesso ao receber 200 com os dois campos `ok`. O cliente usa `/api/health` relativo, servido por proxy no desenvolvimento e pelo servidor da SPA no Compose, evitando URL de API gravada no bundle.

Este endpoint mede prontidão do banco; não há esquema, autenticação, migração ou dados de negócio nesta spec. O teste de indisponibilidade deve provocar falha real de conexão/consulta em uma instância controlada e verificar o status e corpo, além de testar separadamente a falha de rede vista pela tela.

## Decisões e alternativas

- **Alinhar o harness ao perfil do projeto.** Alternativa: substituir apenas nomes no índice. Isso deixaria comandos, gates, papéis e skills incompatíveis com o perfil técnico ativo.
- **`GET /api/health` consulta o PostgreSQL em toda chamada.** Alternativa: responder sempre 200 quando o processo FastAPI está vivo. Isso não demonstra comunicação entre as três partes nem detecta banco indisponível. Usar consulta curta e timeout evita uma tela indefinidamente carregando.
- **`psycopg` direto, sem modelo de domínio ou migração.** Alternativa: iniciar SQLAlchemy/Alembic com tabela artificial. Uma tabela criada apenas para health aumenta a superfície de manutenção sem satisfazer outro requisito; introduzir persistência de domínio quando a primeira feature exigir.
- **Backend e frontend em imagens separadas, com proxy `/api`.** Alternativa: URL absoluta da API embutida no build React. O proxy mantém o mesmo caminho no desenvolvimento e na entrega e permite trocar o destino sem rebuild da UI.
- **Conservar o check `CI` e a promoção existente.** Alternativa: criar novos nomes de check ou publicar direto da branch de feature. Isso exigiria mudança nas proteções e confundiria a linha de release; a stack muda, o fluxo de revisão e promoção permanece.

## Riscos e evidência esperada

- As deleções locais ainda não estão na branch: comparar o inventário antes/depois do transporte e revisar o diff para impedir perda de `designsystem/` ou de dados persistentes.
- O volume PostgreSQL anterior pode conter banco/usuário/esquema diferentes: documentar a configuração e demonstrar o fluxo com volume novo e isolado, sem destruir o antigo. Não interpretar falha de credencial como sucesso.
- O proxy da SPA e o do Vite podem divergir: teste de interface simula respostas e falha de rede; teste ponta a ponta local usa os três serviços e verifica sucesso e indisponibilidade.
- Reescrever instruções pode deixar referências obsoletas: varrer todos os arquivos do projeto e revisar cada ocorrência remanescente com seu contexto.
- CI verde só prova o que executou: registrar comando, contagem de testes e resultado em `verification.md`; exigir resultado do workflow `CI` na PR. Publicação GHCR, Project e implantação externa dependem de ambiente/permissão e não serão declaradas verificadas sem execução.
